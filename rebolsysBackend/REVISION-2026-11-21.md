# Revisión de REBOLSYS: reservas, validaciones y limpieza de código

Fecha: 21 de noviembre de 2026, America/Lima.

## Alcance y decisión funcional

Se revisaron transversalmente los dos proyectos REBOLSYS: flujo de reservas y
cuentas, integración con ventas y limpieza, validación de entradas, manejo de
errores, rutas Angular, dependencias del código fuente y suites disponibles.
Los proyectos Pharma, el material de cursos y los scripts históricos de Oracle
quedan fuera del sistema operativo REBOLSYS y se conservaron.

Decisión confirmada por el usuario: finalizar automáticamente las estancias en
curso cuando llegue o venza su checkout, siempre que no tengan deuda; la habitación
debe quedar POR_LIMPIAR. No se confirma una reserva que nunca registró ingreso.

## Hallazgos corregidos

| Hallazgo | Cambio | Evidencia |
| --- | --- | --- |
| Las estancias solo salían mediante una acción manual. | Tarea cada 60 segundos, primera ejecución tras 10 segundos, hora de Lima. Recupera vencimientos anteriores al arranque. | Pruebas de frontera temporal, recuperación histórica y consulta de candidatas. |
| Sumar saldos podía ocultar una deuda mediante un sobrepago de otra cuenta. | Checkout manual y automático exigen saldo cero individual en alojamiento y cada cuenta de consumo. Solo cuentan pagos verificados. | Prueba con alojamiento sobrepagado y consumo impago cuyo saldo agregado es cero; prueba de pago no verificado y posterior regularización. |
| Una estancia ya leída podía quedar en caché después de finalizarse en otra transacción. | Refrescar el detalle bloqueado al registrar una venta asociada. | Prueba con un contexto JPA que conserva EN_CURSO y un checkout confirmado mediante REQUIRES_NEW: el consumo se rechaza sin guardar venta ni alterar stock. |
| Se podían crear reservas cuyo checkout ya había pasado. | Rechazo antes de guardar o cobrar. Los reintentos válidos siguen recuperándose por clave antes de esta comprobación. | Pruebas de fecha vencida, fechas invertidas y rollback. |
| Omitir parámetros obligatorios podía terminar en el manejador genérico de error 500. | Respuesta 400 con nombre del parámetro y mensaje de validación. | Casos reales de controladores de habitaciones, gastos y consulta de clientes mediante MockMvc. |
| Consulta de clientes aceptaba identificador no positivo y documento vacío. | Restricciones en el controlador: tipo positivo, documento no blanco, máximo 50 caracteres. | Pruebas de nulos, blancos y parámetros ausentes. |
| Métodos públicos de creación y actualización de personas dependían de la validación del llamador. | Validar también al entrar al servicio. | Llamadas directas con identidad inválida rechazadas antes de modificar la ficha. |
| La lista abierta no reflejaba cambios del servidor por sí sola. | Recarga silenciosa cada 30 segundos; evita solapamientos y pausa con detalle, pago, comprobante u operación activa. El detalle consulta el estado vigente. | Siete pruebas Angular de actualización, pausas, red lenta, errores, destrucción y respuestas fuera de orden. |

## Garantías del checkout automático

- Selecciona exclusivamente detalles EN_CURSO con `fechaSalida <= ahora`.
- Procesa lotes de 100 identificadores ordenados y avanza por el último ID,
  evitando saltos cuando se retiran filas del conjunto de candidatas. Las deudas
  del primer lote no impiden atender lotes posteriores.
- Cada estancia tiene una transacción independiente. Un fallo se registra y se
  reintenta en el próximo ciclo; no revierte las salidas que ya terminaron.
- Respeta el orden de bloqueo existente: reserva, habitación y detalle. Refresca
  habitación y detalle después de bloquear. Dos instancias o una salida manual
  simultánea no finalizan dos veces el mismo detalle.
- Usa la misma regla de salida que el checkout manual; impide salida anterior
  al ingreso real y conserva los controles financieros.
- No genera pagos, devoluciones, movimientos de caja ni comprobantes nuevos.
- No pisa un estado físico inconsistente, como una habitación en mantenimiento;
  registra el error para revisión y conserva la estancia.
- Guarda `fechaSalidaReal` con la hora del procesamiento. Si el backend estuvo
  apagado, no se presenta la hora programada como una salida real observada.
- Registra dos actualizaciones en AUDITORIA_GENERAL, para DETALLE_RESERVA y
  HABITACION, identificadas como CHECKOUT_AUTOMATICO. El actor queda nulo porque
  es una operación del sistema; no se atribuye al operador que creó la reserva.
- GET permanece solo lectura. Las reservas con deuda conservan EN_CURSO. Tras
  liquidarlas, el siguiente ciclo puede cerrarlas. Una habitación POR_LIMPIAR
  sigue bloqueada para nuevas reservas hasta completar el flujo de limpieza.

## Código retirado y conservado

Se analizó el grafo de imports estáticos y dinámicos desde `src/main.ts` con el
compilador TypeScript y se contrastaron rutas, selectores, plantillas y referencias.
La pantalla genérica `features/configuraciones/pages/configuracion-list` ya no era
alcanzable. Las rutas actuales cargan los módulos específicos de habitaciones,
mobiliario y productos.

Se retiraron cinco archivos de esa implementación antigua: TypeScript, HTML y CSS
del componente, su servicio exclusivo y su modelo exclusivo; sumaban 916 líneas.
Sus cuatro pruebas solo ejercitaban la pantalla retirada. Se conservaron localmente
en `rebolsysFrontend/.local/revision-2026-11-21/configuracion-list.spec.ts`, fuera
de la suite activa. No se retiraron pantallas ni funcionalidades accesibles.

También se eliminaron 53 importaciones Java sin uso y la generación de una clave
de pago Angular que nunca se consultaba. La transición de salida manual y
automática comparte `SalidaReservaGestion`, evitando duplicar el cambio de estados.
Las pruebas de listado y servicio de reservas cuentan con excepciones explícitas
en `.gitignore` para poder versionarlas.

Se conservaron `environment.development.ts`, usado mediante reemplazo de archivos
en Angular, los contratos de compatibilidad y los scripts históricos de base de
datos. Los campos que inicializan `notificarCambios` producen efectos de Angular:
aunque el análisis `noUnusedLocals` los señale por no leer su referencia, eliminarlos
suprimiría avisos. No se trataron como código muerto.

## Pruebas ejecutadas y resultados

Entorno: Java 21.0.12.1, Node 24.19.0, npm 11.17.0; dependencias ya instaladas.
Las pruebas nuevas de transacciones usan H2 aislado en modo Oracle, no la base
operativa. Los proveedores y correos se simulan en las suites correspondientes.
La planificación de fondo queda deshabilitada en `src/test/resources/application.properties`;
los escenarios invocan explícitamente el procesamiento para mantener determinismo.

| Comprobación final | Resultado |
| --- | --- |
| `rebolsysBackend`: `mvnw.cmd clean package`, incluida toda la suite JUnit | BUILD SUCCESS; 337 casos descubiertos, 228 aprobados, 109 omitidos, 0 fallos y 0 errores. JAR ejecutable generado. |
| `rebolsysFrontend`: `npm test -- --watch=false` | 165 aprobados, 6 omitidos; 30 archivos aprobados y 4 archivos omitidos. |
| `rebolsysFrontend`: `npm run build` | Compilación de producción correcta; tres advertencias de presupuesto CSS. |

Antes del cambio, las suites locales ejecutaron 113 pruebas backend y 162 frontend
con éxito. La suite backend creció en 115 casos ejecutados. El frontend incorpora
7 casos nuevos y retira 4 de la pantalla obsoleta: 165 casos activos aprobados.

`ValidacionesEntradaTest` aporta 94 casos sobre los controladores reales con
servicios simulados. Comprueba cuerpos y parámetros inválidos y verifica que no se
invoque el negocio: importes negativos, precisión y límites monetarios, nulos en
colecciones y objetos anidados, cantidades y stock fuera de rango, campos vacíos o
demasiado largos, enums desconocidos, evidencias inválidas, datos de arqueo,
paginación y parámetros obligatorios. Son pruebas MockMvc dentro del proceso,
no llamadas HTTP a un servidor desplegado.

`CobroInmediatoIntegracionTest` amplía los escenarios con persistencia y
transacciones reales H2: fechas y estados, pagos e idempotencia, deuda histórica,
deuda compensada artificialmente, simultaneidad de salidas, caché JPA, rollback,
solapamientos de reservas, habitaciones repetidas, ocupantes duplicados, titular
menor de edad, responsables de menores y el límite de siete años para plaza sin cama.
`CheckoutAutomaticoTest` verifica también el recorrido de varios lotes y la
continuación ante un fallo individual.

Se ejecutaron asimismo las suites existentes de JWT y permisos, sesión y actor
HTTP, contratos JSON, modelo de entidades, limpieza y mantenimiento, inventario,
cobros, documentos fiscales, PDF y entrega de comprobantes. Los controles con
filtros de seguridad activos están en `AccesoHttpTest`; las pruebas de reglas de
negocio con `MockMvcReglasNegocio` desactivan filtros deliberadamente.

### Comprobaciones no ejecutadas y límites

Los 109 casos backend omitidos corresponden a 102 dependientes de Oracle
(`PropuestaOracleTest`: 67; `GastosOracleTest`: 12;
`FacturacionElectronicaOracleTest`: 9; `ConcurrenciaOracleTest`: 6;
`RebolsysBackendApplicationTests`: 8) y 7 que requieren el simulador HTTP externo
de consulta de documentos (`RUN_APISPERU_SIM_TESTS`).

Los 6 casos frontend omitidos requieren URLs de simulaciones HTTP de Postman
para altas de productos, carga y pago de ventas y entrega de comprobantes.
No se levantaron esos simuladores ni se enviaron solicitudes a proveedores reales.
Parte de los specs previos sigue siendo local y está ignorada por Git; el total
de pruebas de un checkout limpio puede ser menor que el de este espacio de trabajo.

H2 comprueba transacciones y persistencia de estas pruebas, pero no reproduce los
triggers, restricciones manuales, bloqueos ni todos los comportamientos LOB de
Oracle. Falta verificar la integración en un esquema Oracle de desarrollo
actualizado antes de desplegar. La ejecución no certifica ausencia absoluta de
defectos ni cobertura completa de todas las ramas. No se modificó el esquema ni
se actualizaron registros operativos durante esta revisión.

La compilación Angular conserva advertencias CSS en `habitacion-list` (4.38 kB),
`venta-form` (4.13 kB) y `reserva-form` (4.04 kB), por encima del aviso de 4 kB y
por debajo del límite de error de 8 kB. No impiden generar el sitio.

## Reproducción y puesta en marcha

Desde `rebolsysBackend`, con Java 21 configurado en JAVA_HOME:

```powershell
.\mvnw.cmd clean package
# Solo los grupos nuevos/ampliados:
.\mvnw.cmd '-Dtest=CheckoutAutomaticoTest,CobroInmediatoIntegracionTest,ValidacionesEntradaTest' test
```

Desde `rebolsysFrontend`, con Node 24 y las dependencias instaladas:

```powershell
npm test -- --watch=false
npm run build
```

Los registros de esta sesión quedan en los archivos locales ignorados
`rebolsysBackend/.local-revision-backend.log`,
`rebolsysFrontend/.local-revision-frontend.log` y
`rebolsysFrontend/.local-revision-build.log`. Surefire conserva el detalle XML
por suite en `rebolsysBackend/target/surefire-reports`.

Para activar el cambio en una instalación, desplegar o reiniciar el backend
actualizado y servir la nueva compilación frontend. No hay migraciones SQL.
La configuración predeterminada es:

| Variable de entorno | Valor | Significado |
| --- | --- | --- |
| CHECKOUT_AUTOMATICO_HABILITADO | true | Habilita la revisión automática. |
| CHECKOUT_AUTOMATICO_INTERVALO | 60000 | Milisegundos entre el fin de un ciclo y el inicio del siguiente. |
| CHECKOUT_AUTOMATICO_ESPERA_INICIAL | 10000 | Milisegundos antes del primer ciclo tras arrancar. |

En una base de desarrollo, comprobar después del despliegue una estancia vencida
pagada, una con deuda, una reserva de varias habitaciones con vencimientos
distintos y el flujo posterior de limpieza. La ventana normal de actualización
es un ciclo backend más hasta 30 segundos del frontend; puede aumentar por carga,
bloqueos, fallos o pestañas que el navegador mantenga en segundo plano.
